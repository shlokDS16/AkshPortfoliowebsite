## Measurements (Node 24.14, Core Ultra 9 275HX, 34 GB; recorded again in the spec)
Realistic at-cap workbook (100,000 cells = 80,000 constants + 20,000 formulas: 18,000 chain cells, 1,950 100-cell SUMs, 50 SUMs over blocks of up to 80,000 cells; every saved value computed independently, so all 20,000 match):
- File 660 KB. Whole read **769 ms**: scan 12, SheetJS parse 153, graph 232, IronCalc load 101, evaluate 133, read values 14, diff/taint/suggest/report 110. Peak RSS 399 MB against the test runner's own 184 MB (about 215 MB for the read). Stored object 4.6 MB (engine bytes 1.3 MB base64). Well inside the 60 s / 1 GB lines, so the numeric caps stay.
- wasm 0.8.4 (run in Node's V8): load 217 ms; `evaluate()` alone 200 ms; one input change + `evaluate()` + read 156-260 ms; 25 changes (a 5 x 5 grid) **5.3 s**. wasm evaluates on every `setUserInput` unless `pauseEvaluation()` is called; before the fix it was 330-440 ms per change and 9.3 s per grid. The wrapper now pauses around input batches. IronCalc re-evaluates the whole workbook each time (no incremental recalc).
- **D18 is triggered in practice.** 160-260 ms is under the spec's 250 ms line on this machine, but the grid is 5 s, and a phone is several times slower. Recommendation: Task 3 builds the Web Worker and runs the grid there.
Adversarial shapes the cell caps do not bound (this is the main finding):
- 20,000 formulas that each `SUM` the same 80,000 cells: evaluate **96 s** (over the 60 s line). 500 x `SUMPRODUCT` of two 80,000-cell blocks: 5.7-7 s. 500 x `SUM` of the block: 1.4-2.3 s.
- Whole-column references: `SUM(A:A)`, `SUMIF`, `COUNTIF`, `XLOOKUP`, `NPV` stop at the last filled cell (~0 ms), but `MAX(A:CV)` is 1.1 s per formula, `MATCH(x,A:A,0)` 35 ms, `VLOOKUP(x,A:B,..)` 25 ms, `SUMPRODUCT(A:A,B:B)` 0.4 s, `SUMPRODUCT((A:A>5)*(B:B>2))` 1.4 s.
- Fix: `cost.ts` estimates the engine's time from the reference graph (per range use: cells filled for ordinary functions, cells declared for a measured list of scanning and array functions, the whole workbook for OFFSET/INDIRECT cells) and `build-model` refuses above 30 s (`too_complex`) before the engine starts. The estimate is above every measurement (192 ms estimated vs 133-200 ms measured for the realistic case; 7x above for plain SUMPRODUCT). The 20,000 x SUM and 500 x SUMPRODUCT shapes are now refused in 130-290 ms. Residual: a range inside array arithmetic that is itself inside another function (`SUM(IF(A:A>5,B:B,0))`, 0.8 s per formula) is not recognised; at most about 35 such formulas fit before the function's own timeout, which is the spec's designed degrade path (lease expiry, second expiry to needs_attention).

## Findings about the libraries (all pinned by tests where possible)
- IronCalc 0.8.3 cannot open a workbook that contains an Excel data table (What-If Analysis): `Model.fromXlsx` throws "Not Implemented Error: data table formulas". Found on 2 of 80 real files; it is its own refusal `data_tables` with the Excel fix in the sentence. Valuation models use data tables for sensitivities, so Aksh will hit this; the message tells him to paste values.
- `INDIRECT("Sheet!A1")` (sheet-qualified text) is `#VALUE!` once imported from a file, but works when typed into a fresh model; same-sheet INDIRECT works. The importer wraps it as `=@INDIRECT(...)`. The desk reports such a cell as `differs`, so it is tainted and never offered as a result. A test pins this: if IronCalc fixes it the test fails and the limit can be lifted.
- Cells downstream of `TODAY()` differ from the saved values (date drift) and are `differs`; only the `TODAY()` cell itself is `dated`. A real workbook showed 44 such cells. The report (Task 3) may want to group them.
- Real Excel files store `_xlfn.IFS` / `_xlfn.XLOOKUP` etc.; IronCalc reads them correctly (checked on 21 functions); SheetJS already strips the prefix, and `read-workbook` strips again defensively.
- IronCalc function gaps seen: `FORECAST.ETS`, `TEXTSPLIT`, `UNIQUE`/`FILTER`/`SORT` (spill errors), `MDETERM`, `MINVERSE`, `AGGREGATE`, `HYPERLINK`. They surface as `unsupported` with the function named (`probeFunctions` asks a scratch engine which names it lacks). Error text is `#N/IMPL!` (with the bang); both spellings map to one kind. I did not find a function that returns it, so the NIMPL branch of the diff is covered with a synthetic value.
- `Model.fromXlsx(path, "en", "Asia/Kolkata", "en")`: accepted. `en-IN` is not a locale of the package (supported: es, de, en, fr, it, en-GB). `getAllTimezones()` lists `Asia/Calcutta`, but `Asia/Kolkata` is accepted too.
- wasm 0.8.4 `getTokens` takes formulas with or without the leading `=`; it returns `Illegal` for 3D references (`Sheet1:Sheet3!A1`), which the graph treats as dynamic. Structured references and `#` spill references are also dynamic.
- Number format round trip: setting `0.2` into a `0.0%` cell via `setUserInput` gives 20.0% (not 0.2%), so the UI's percent editing (11.5 -> 0.115) is right. wasm `getFormattedCellValue` with `0.00000000000000E+00` gives 15 significant digits, and equals `Number(raw.toPrecision(15))` for every numeric cell of the fixture; exponents print as `E-00` for zero exponent, which `Number()` parses.

## Security pass (defenso)
`ToolSearch` is not in this agent's tool set and no defenso tool is exposed, so `guard_code` was NOT run. A manual pass over `zip-scan.ts`, `read-workbook.ts`, `engine-node.ts`, `tokens.ts`, `build-model.ts` found and fixed:
- Two quadratic regular expressions on hostile text (`<row ` openers with no `>`: 40,000 took 1 s with the unbounded pattern, 11 ms bounded; the same for the `.bin` content-type default). Now length-bounded, with tests on 2 million openers.
- A sheet-name or defined-name of unbounded length would be repeated in every cell key; now Excel's own limits (31 / 255) are enforced, plus number formats (255) and a running stored-size count.
- SheetJS silently drops rows past `sheetRows` (and `!fullref` is only set when the dimension tag says so); rows past 20,000 are now refused from the raw XML before the parse.
- SheetJS-written files declare `application/vnd.ms-excel.sheet.binary.macroEnabled.main` as the `.bin` default; a naive macro check refused every SheetJS file. The check now ignores the `.bin` default and refuses macro overrides, VBA parts by name, VBA relationships and `xl/macrosheets/`.
Other properties verified by tests: no `process.env`, no secret, no service-role client, no `fetch`/`eval`/`innerHTML`/`console.*` in the module; `server-only` on every file that loads a native or parsing library; `xlsx` imported only in `read-workbook.ts`, `@ironcalc/nodejs` only in `engine-node.ts`, `@ironcalc/wasm` only in `engine-client.ts` and `tokens.ts`; no import from the public site, showcase or compliance module; the module's strings contain none of the banned advice words; refusal messages are fixed sentences and a test shows a hostile defined-name text never reaches one. The temp file has a random name (`desk-xlsx-<uuid>.xlsx`), mode 0600, and is deleted in `finally` (tests: after success, after a thrown engine error). Zip scan: entry names are only compared with fixed strings; local-header/central-directory names must match; duplicate (case-insensitive) names, overlapping data, zip64, split archives, encryption, odd methods, bytes between the directory and the end record are refused; each entry is really inflated with `maxOutputLength = declared size` and checked for size and CRC; 4,000-run mutation fuzz in `zip-scan.test.ts` only ever throws `XlsxRefusal`.
Recommended for the Opus review: (1) the cost-estimate constants in `cost.ts` (measured, deliberately high); (2) `zip-scan.ts` against zip shapes I did not think of (for example local headers that overlap another entry's header; only data ranges are checked for overlap); (3) whether to run the engine in a child process that can be killed on a deadline instead of relying on the estimate (the native `evaluate()` cannot be interrupted).
