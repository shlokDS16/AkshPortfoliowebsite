## Open (2026-10-13, real-provider smoke batch)
- **Q24 (security, Shlok: approve or reject, own commit so it can be reverted alone):** www.bseindia.com answers with a header byte Node's strict HTTP parser refuses (HPE_INVALID_HEADER_TOKEN), so every BSE link failed. Built: for hosts under `bseindia.com` only (fixed list `LENIENT_PARSER_HOSTS` in `src/modules/documents/safe-fetch-transport.ts`, dot-boundary match), when the strict request fails with exactly that error, the same hop is retried once with `insecureHTTPParser`; all other checks (https only, vetted pinned address, caps, redirect re-validation, content rules) are unchanged and no other host is ever lenient.
  Trade-off: a lenient parser on those hops accepts malformed headers (the usual risk is request/response smuggling through a proxy), which here is limited to one GET with no keep-alive, no cookies, a vetted address and a response read only as bytes; if BSE is ever compromised its malformed headers are accepted. Reject = revert the commit "fix(documents): open bseindia.com pages..." and paste text or upload the PDF for BSE. Real check 2026-10-13: the announcements page opened (HTTP 200, 14,287 bytes) after one lenient retry.
  Added after the batch-B review (2026-10-13), in plain words: Node has no switch for one rule, so `insecureHTTPParser` turns on every leniency of its parser, not just the bad header byte. Measured by the reviewer on Node 24.14.0 (llhttp 9.3.0), the lenient attempt also admits: LF-only line endings (a bare LF inside a header value starts a new header, so BSE could make a line it sent read as a header it did not mean); `Content-Length` together with `Transfer-Encoding: chunked` (chunked wins); obs-fold continuation lines; and any HTTP version number. It still refuses invalid header names, a bare CR and two differing `Content-Length` values. Which of these are admitted is decided by the Node release in production and has widened before. What keeps it contained: the size cap (`LINK_MAX_BYTES`, the upload limit) and the 30 s time cap apply to the lenient hop too, the connection goes only to the vetted pinned address, every attempt opens its own connection (`agent: false`, so nothing is reused or shared), and each redirect hop is strict again. Residual risk: if BSE (or something on its path) is compromised, it can shape the headers of the answer we read, for example the type, length or redirect target we see; all of that is still re-checked by the same content and redirect rules, and the answer is only ever read as bytes. The retry fires only on `HPE_INVALID_HEADER_TOKEN`; tests pin that a reset connection and an LF-only answer are not retried.
